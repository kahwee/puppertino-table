# Verification

Use pnpm 12.15.0 and Node 24.22.1 to match CI. `pnpm check` runs the full local gate. Keep generated `dist` committed for Git installs and verify it matches a fresh build.

## CI lanes

GitHub Actions runs the same gates as `pnpm check` in seven independent runner jobs: quality (lint/types/unit tests), packed-consumer verification (including a fresh library build and checked-in `dist` comparison), demo/hydration, and four Storybook suites (interactions, tables, Finder workflows and docs). The Storybook interaction runner reuses an empty host and caches shared assets, while each story receives a fresh iframe to isolate its state. Each browser job builds its own fixture; Storybook suites use separate runners and browser contexts. `PUPPERTINO_BROWSER_SUITE=demo` or `stories` selects a shard; the default local browser command runs every suite with concurrency capped at two. Use `stories-interactions`, `stories-table`, `stories-finder` or `stories-docs` to run one Storybook suite. Only browser jobs install Chromium; its download is cached by OS, architecture and lockfile. CI, npm preparation and release verification share this workflow. Release jobs download the already-verified package instead of rebuilding it, then retain the exact-tag, SHA and integrity checks. Pages deployment and npm publication wait for every verification job; superseded pull-request runs are cancelled. This trades additional runner minutes for a shorter critical path. Media is kept in the repository and Pages, outside the npm package. See [media capture](https://github.com/kahwee/puppertino-table/blob/main/docs/media/README.md), [releasing](https://github.com/kahwee/puppertino-table/blob/main/RELEASING.md) and [pointer profiling](https://github.com/kahwee/puppertino-table/blob/main/docs/pointer-performance.md).

Within the quality lane, lint, type checking and unit/release tests run concurrently. The collection benchmark starts only after all three succeed, so those checks do not compete with its timing samples. Builds and consumers remain in their separate lanes; artifact identities, release permissions and the all-lanes deployment gate are unchanged.
